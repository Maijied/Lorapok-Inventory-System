# Android

The only file here that is hand-written is `twa-manifest.json`. Everything
else a Trusted Web Activity needs — the Gradle project, the manifest, the
resources — is generated by `bubblewrap init` during a release. Several
thousand generated files rebuilt identically on every release are cost
without benefit, and they would bury the one file worth reviewing in a diff.

## Why one app, not one per shop

A TWA is trusted for exactly one origin, and Digital Asset Links has **no
wildcard** — `*.lorapok.tech` cannot be expressed. So the app binds to the
apex and a shop signs in with its own address.

Per-shop would mean an APK, a Play listing and a Play review each, and a shop
provisioned after the last release would get an app that silently degrades to
a browser tab with a URL bar.

## What has to line up

`packageId` here, the `ANDROID_PACKAGE` variable, and the `package_name` the
site serves at `/.well-known/assetlinks.json` must all match. So must the
signing fingerprint and `ANDROID_CERT_SHA256`.

When they do not, nothing errors. The app installs, opens, and shows a URL
bar — which is the hardest kind of failure to attribute after the fact. The
release workflow checks the fingerprint for that reason.

`host` and `startUrl` point at production. Changing them is a real decision,
not configuration: an app built against a staging host is trusted for staging
and nowhere else.

See `docs/releasing.md` for the secrets.
